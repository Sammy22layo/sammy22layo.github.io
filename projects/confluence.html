Case study

Two marketplaces, one set of numbers

A Brazilian e-commerce platform acquires a South African one — different systems, different currencies, different definitions of "late". This is the platform that reconciles them into one warehouse with a single point-in-time financial truth.

Architecture

The problem

Confluence Group runs a Brazilian marketplace and has acquired a South African one on a different platform. Three things are broken.

  • Revenue keeps moving. Finance restates history at today's FX rate each month, so last quarter's USD figure is different every time it's reported.
  • Operations cannot compare the platforms. Each defines a delivery promise differently — Brazil measures from purchase, South Africa from dispatch.
  • Commission may be double-paid. Some merchants sell on both platforms under slightly different names, and nothing links them.

What the build delivers: one conformed warehouse, one merchant master carrying full history, revenue fixed at the rate that applied on the day, and a model that sets a delivery promise per order at a service level the business chooses.

Decisions worth defending

The watermark ceiling is frozen before the copy runs, not after

Setting the watermark to "now" when a load finishes loses every row that arrived mid-run. The copy had already read its data before those rows existed, and the watermark has since moved past them — so they're skipped by that run and excluded from the next, silently and permanently. usp_StartRun freezes the ceiling first; usp_EndRun advances to that frozen value, and only on success.

The quality gate halts the load rather than writing what passed

Above a 5% quarantine rate nothing is written — not even the good rows. When a tenth of a file fails, the likeliest cause is that something changed: a date format flipped, a delimiter shifted. The 90% that passed are then suspect too, because they passed a check asking the wrong question.

A partial load makes a dashboard quietly wrong. An unchanged table and a red pipeline are unambiguous.

SCD2 validity windows end one day before the next version begins

date_sub(lead(snapshot_date), 1) rather than lead(snapshot_date). Without the subtraction the handover date falls inside two windows, the fact table's BETWEEN join matches both rows, and that order's revenue is counted twice. Nothing errors — the totals are simply wrong. Verified at zero overlapping windows across 5,982 versions.

Related, and the reason the dimension exists at all: the fact table joins on a date range, never on is_current. Joining on is_current runs fine, produces one row per order, and applies today's commission rate to every historical sale — discarding the entire point of building SCD2.

Unresolved merchant matches are left unmerged

Three buckets, not two: MATCH, REVIEW, NO_MATCH. Two rows for one merchant understates that merchant's revenue and is visible when someone notices the duplicate. One wrongly merged row attributes revenue to a business that did not earn it, and is invisible. 28 pairs sit in REVIEW with their scores and margins, waiting for a human.

Every ML feature is knowable at checkout

The merchant's trailing delivery average uses rowsBetween(-50, -1) — the previous 50 orders, stopping one short of the current one. With 0 instead of -1 the feature contains a slice of the answer, the model scores beautifully, and it collapses in production. The train/test split is chronological, and the test window is trimmed 30 days short of the data end because slow deliveries near the cutoff never appear as delivered.

Exchange rates carry forward; they are never interpolated

Friday's close is the last price that actually existed. An interpolated Saturday rate is a number nobody traded at. rate_source records published or carried on every row, so any figure can be audited without re-deriving it.

The delivery promise model

Three quantile regressions — p50, p90, p95 — trained on 107,177 orders and tested on 19,150 the model had never seen. The business picks the service level; the model sets the date per order.

Three features carry nearly all the signal: destination region (0.1045), the merchant's trailing delivery average (0.0632) and freight cost (0.0478). Weather contributed nothing measurable — trailing rainfall doesn't reach the top twelve, because destination already encodes climate. Reported as a negative result rather than quietly dropped.

Evidence

Azure credits expire and take the factory, the database and the audit table with them. All of this was exported while it was live.

  • The run log. Every run with timestamps, file counts, and two deliberately triggered failure types with their error text. A log showing only successes looks like a pipeline nobody tested.
  • The manifest export. Read the rows and you understand immediately why there are two pipelines instead of eighteen.
  • The pipeline JSON in Git. The ARM template export is in the repository, so the code is reviewable whether or not the factory still exists.
  • Layer-by-layer walkthroughs. Every notebook cell carries its reasoning beside the code, and docs/walkthroughs/ explains each layer line by line — including the errors hit and how each was resolved.

On the data

The Brazilian side is the public Olist dataset — 99,441 orders, 112,650 items and 3,095 sellers between September 2016 and October 2018 — joined to live ECB reference rates, public holiday data and 24,084 daily weather observations across 36 regions.

The South African platform is synthetic, generated from the real Olist seller and order data so the cross-platform merchant overlap is genuine rather than invented. It deliberately carries different column names, day-first dates, semicolon delimiters, ZAR amounts, a column that appears partway through the period, and monthly merchant snapshots in which tier, commission rate and status genuinely change.

This is disclosed rather than hidden. No public dataset offers two marketplaces on incompatible systems with overlapping merchants, which is precisely the problem this build exists to solve.

Limitations

Recorded rather than hidden. Each was a deliberate decision with a cost attached.

  • 329 orders from the 2016 Olist pilot are quarantined. The FX window starts 2016-12-30, so those dates have no rate to carry forward from. Widening the window would fix it; the quarantine was kept because a gate catching 329 rows for a stated reason is itself evidence the gate works.
  • 76 of 120 known merchant pairs are undecidable from name alone. Geography can't break the tie, because the same business has different addresses in each country.
  • Refunds are ingested but not modelled. They land in bronze; silver doesn't yet consume them, so late-arriving refund facts aren't implemented.
  • The ZA product catalogue doesn't exist. The generator produced SKUs without product attributes, so category, weight and volume are null on that platform. Carried as typed nulls rather than invented values.
  • Delivery promises aren't directly comparable across platforms. Brazil measures from purchase, South Africa from dispatch. Both are stored as given, with promise_basis exposed as a column, so any comparison must slice by it.
